The Scaling Problem

  Integration barrier

Public HTTP endpoint required, a blocker for HPC clusters and university firewalls.

  Throughput limitations

Online inference architecture used in a batch setting.

Architecture: Original Push Model

  Who determines the throughput?

Each worker has different capacity, each pipeline has different requirements. Result: low GPU utilization.

Architecture: Redesigned Pull Model

Inverting the direction: PS workers poll Antenna's job queue — no public endpoint needed, and each additional worker adds capacity automatically.

Architecture: Invert the dependency

Workers from different institutions register their available pipelines at startup. Antenna publishes tasks to a job queue. Heterogeneous hardware coexists without central configuration.

  No central configuration

Workers self-describe their capabilities. Add a new institution by running a worker, not by editing server config.

  Heterogeneous hardware

HPC clusters, university servers, cloud instances: each runs the pipelines it has.

Pull Architecture: What Changed

Inverting the model shifts control to the workers.

  Workers control their own pace

Each worker polls for exactly as many jobs as it can handle.

  Througput scales with capacity

Add more workers to scale out.

  GPUs are no longer starved

Workers stay busy as long as there is work in the queue. With starvation eliminated, the bottleneck shifts to the pipeline itself.

Architecture: Results

  Deploy anywhere

Workers run anywhere with outbound HTTP: HPC clusters, firewalled networks, local machines.

  Multi-institution

Workers can span institutions and different hardware, no uniformity needed.

  Horizontal scaling

Add workers without changing Antenna; each independently polls and claims batches.

Inverting push/pull → workers control the speed.

Architecture: Production Reliability

Getting to 108s is one problem. Keeping a 42K-image job from silently failing at image 38K is another. Four pieces of work address the failure modes.

  NATS dead letter queue

Failed or unprocessable messages are captured and inspectable rather than silently dropped. Failed jobs surface immediately.

  Atomic Redis operations

Distributed locks replaced with SET NX and atomic transactions. No deadlocks under concurrent workers competing for the same task.

  Job cancellation

Workers can abort in-flight jobs cleanly. Redis errors propagate as explicit job failures rather than silent hangs in the UI.

  Celery state alignment

Async job state tracks the Celery task lifecycle correctly, so job status in the UI reflects what workers are actually doing.

Open Science and Sustainability

Biodiversity research generates data faster than most groups can build pipelines to process it. That gap is an RSE problem, not a science problem.

  Fully open source

Both Antenna and ami-data-companion are public. Any institution can run a worker or fork the platform.

  Versioned pipelines

ML pipelines are registered by name and version. Workers self-describe their capabilities; Antenna routes accordingly.

  End-to-end test infrastructure

Management commands drive full ML job runs in CI. Async result paths and job state machines are covered by integration tests.

  The RSE capacity gap

Most ecology groups collect more data than they can process. Shared infrastructure like this scales RSE effort across institutions.

Optimization: Data Loading

With num_workers=0, the main thread fetches each image from S3, decodes it, and runs transforms before the GPU can start. Network I/O and decoding dominate, so the GPU spends most of its time waiting.

Fix: num_workers=N runs N worker processes that prefetch and preprocess in parallel, keeping the queue full. pin_memory=True enables DMA transfer directly into GPU-accessible memory.
